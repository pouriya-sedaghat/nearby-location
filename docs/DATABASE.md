## Location storage

`LocationRepository` receives its pool and TTL explicitly; importing the persistence module does not create a connection. Search and cleanup use the same repository TTL.

The existing migration, `migrations/1706300000000_init.js`, creates PostGIS and the `locations` table.

| Column | Type | Constraint or behavior |
| --- | --- | --- |
| `id` | serial primary key | Generated by the migration library's `id` shorthand |
| `user_id` | text | NOT NULL and UNIQUE; one current location per identifier |
| `geom` | geography(Point,4326) | NOT NULL; WGS84 point |
| `updated_at` | timestamptz | NOT NULL; defaults to `now()`; refreshed by upsert |
| `created_at` | timestamptz | NOT NULL; defaults to `now()`; preserved by upsert |

Upsert converts `ST_MakePoint(lng, lat)` with SRID 4326 to geography. Geography distances and radii use meters. The API validates latitude and longitude bounds before executing SQL.

| Index | Type and column | Purpose |
| --- | --- | --- |
| Primary key on `id` | B-tree | Internal row identity |
| UNIQUE on `user_id` | B-tree | Enforces one row and supports the upsert conflict target |
| `locations_geom_gist_idx` | GiST on `geom` | Candidate reduction using `ST_DWithin` |
| `locations_updated_at_idx` | B-tree on `updated_at` | Ordered stale-row selection during cleanup |

## Run migrations

From the project root, for direct Node execution configure `DATABASE_URL` in `.env` or the process environment. Compose constructs this URL and runs pending migrations automatically at startup. Manual direct-execution commands are:

```bash
NODE_ENV=development npm run migrate:up
```

`NODE_ENV` sets runtime mode and does not select an environment filename. Both modes read the same `.env`. For production:

```bash
NODE_ENV=production npm run migrate:up
```

`node-pg-migrate` records applied migrations. Re-running up against a database with recorded migration history should not recreate the table. A manually created table without matching migration history requires reconciliation by the database administrator.

This package contains one migration. The migration role needs permission to create the required objects. PostGIS must be installed on the server, and authorized access to `CREATE EXTENSION` is required; exact privileges depend on the PostgreSQL deployment. Coordinate application-role privileges for queries and scheduled deletion with the database administrator.

**`migrate:down` drops the location table and the PostGIS extension.** Do not use it for an ordinary application-package rollback.

## Read-only schema inspection

These queries do not modify data:

```sql
SELECT version();
SELECT postgis_full_version();

SELECT column_name, data_type, udt_name, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'locations'
ORDER BY ordinal_position;

SELECT indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'public' AND tablename = 'locations';
```

For a different database schema, check the deployment's schema and search_path. Readiness executes only `SELECT 1`; success does not prove that `locations` exists.

## TTL and deletion

Search applies `updated_at >= now() - make_interval(days => TTL)`. Stale locations are excluded even before cleanup runs. A timestamp exactly at the freshness boundary remains valid.

Cleanup runs at startup and according to `CLEANUP_CRON_SCHEDULE`. Each query selects at most `CLEANUP_BATCH_SIZE` rows ordered by update time, with `FOR UPDATE SKIP LOCKED`. The pass continues until a batch deletes fewer rows than the configured size or shutdown requests a stop. An active batch is allowed to finish before pool closure. DELETE also rechecks the stale condition.

The overlap guard is local to each process. Multiple replicas may run their own jobs; row locks and SKIP LOCKED operate in the database. This is application-managed cleanup, not a native PostgreSQL TTL index.

## Persistence and recovery

Compose stores database files in the named `nearby-vm_pgdata` volume (project `nearby-vm`, volume key `pgdata`). Restarting or removing a container alone does not delete it. Removing the volume loses the local database data. See [Operations](OPERATIONS.md) for backups and recovery verification.

Technical reference: [Geography distance in ST_Distance](https://postgis.net/docs/ST_Distance.html).
